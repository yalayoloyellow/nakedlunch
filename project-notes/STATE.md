# STATE — что работает и что дальше (перезапись, не история)

## Разметка интерфейса (три независимо скроллящиеся области)
`.app-shell` (flex row, `height:100vh`) = `.sidebar` (320px фикс., настройки СГРУППИРОВАНЫ — см. ниже — свой скролл) + `.main` (гибкая ширина: `.main-topbar` инфографика-воронка/принято → `.main-body` вывод+принятое, свой скролл → `.input-bar` закреплён снизу, тема/толчок всегда на виду). Реализовано по прямой просьбе владельца («расположение кнопок, пропорции, сколько чему определено места» — не буквальная копия чужого приложения). Старый `.wrap`/`.topbar`/`.knobs`-grid убраны — `.knobs` (2-колоночная сетка) в узком сайдбаре не имеет смысла, ползунки просто в столбик.
- **Инфографика-воронка в топбаре (`PipelineFunnel`, 2026-07-14)** — заменила невнятную строку `кандидатов N → выдача N · nakedlunch N/N`, которая сливала ДВА независимых конвейера и врала (`кандидатов 2000` — это выброшенные при `real_text=1.0` кандидаты ГЕНЕРАТОРА, а не nakedlunch; nakedlunch-часть базы не показывалась вовсе). Компактная строка всегда на виду: `выдача N` + мини-бар композиции + легенда «X генератор · Y книги · Z классика». Клик → дропдаун с двумя воронками: **⚙ Генератор** (словарь 32k → сгенерировано → формальность/тавтология/банальность, на каждой стадии in→out и `−отсеяно` + за какой ползунок отвечает → в выдачу) и **📖 Nakedlunch** (источников · доступно из всего · **рассмотрено = ВСЯ доступная база целиком** (не выборка — см. «Полная база nakedlunch» ниже) · фильтры extendo · классика · в выдачу). Неактивный конвейер — приглушён с причиной. Данные — структурный `funnel` из `api/server.py: _rich_funnel()` (`gen`/`nl`), числа пула из `_nl_pool_counts()`. При `real_text=1.0` генератор физически НЕ запускается (`gen_active = nl_mix < 1.0`) — `generated` честно = 0.
- **Настройки сгруппированы (`renderKnobGroup`/`renderKnob`, 2026-07-14 — «убрать громоздкость»)**: заголовки, привязанные к воронке — **«Из чего собирать»** (Реальный текст, Классика↔Алгоритм) · **«Форма и звук»** (Рифмовка, Строфы, Точность рифм, Мелодичность) · **«Строгость отбора»** (Банальность/Связность — `.knob-group-head` кнопка, СВЁРНУТА по умолчанию через `showAdvanced`; «Новизна» удалена целиком — см. «Убрана оценка предпочтений» ниже). Условное скрытие неактуального: «Точность рифм» только при `rhyme≠none`, «Классика» только при `real_text>0` (показывать живое, не всё-и-задизейблено). В дефолте видно ~4 контрола вместо 8. Компактный режим (фристайл-пауза) переиспользует те же `renderKnob`/группы.
- **Enter генерирует ВЕЗДЕ**, не только в фокусе поля темы (было — жалоба владельца «работает не вне поля ввода»). `.send-btn` (⏎) справа от поля — кликабельная альтернатива, чат-бокс паттерн. Проверено вживую реальным нажатием клавиши без фокуса на input.
- **Буква схемы рифмовки на каждой строке** (`lastScheme[i % lastScheme.length]`) — та же буква, что в самой схеме («абаб» → а,б,а,б,...), не отдельная нумерация. Считается на фронте из `lastScheme` (см. выше), бэкенд не трогается.
- **Подсветка самой рифмующейся части текста (жирным + акцентным цветом), не только буквы/ключа сбоку** — предложение владельца 2026-07-14 как способ ДЕБАЖИТЬ рифмо-баги глазами по реальному тексту, а не по абстрактному ключу («если жирным раскрасить ударную рифму — сразу видно, где проблема»; ровно так он сам нашёл том/парне в Раунде 14). Бэкенд считает `rhyme_span` (RAW-позиция хвоста в тексте, НЕ то же самое, что редуцированный/оглушённый `rhyme`-ключ) — для сгенерированных строк в `core/scan.py` (инвариант: длина хвоста == длина ключа всегда, редукция/оглушение посимвольные), для nakedlunch — в `tools/build_nl_rhyme.py` через позиции токенов (`core/data/nl_rhyme.json` сменил формат на `{text: {"key","span"}}`, пересобран с нуля). Фронт — `RhymeText({text, span})`, оборачивает диапазон в `.rhyme-hl` (жирный/акцент/подчёркивание), подключено в основном списке и во фристайле; панель принятого не трогается (там только текст, дебажить нечего). Проверено вживую: реальная сломанная пара («лёд и асфальт» ~альт / «трио и боязнь» ~язнь, обе с буквой «а») видна с первого взгляда — подсвеченные хвосты явно разные, без похода в JSON.
- **Инлайн + на каждой строке** — в избранное кликом, не только строку под клавиатурным курсором (кнопка «−»/отклонить УБРАНА целиком 2026-07-14, см. «Убрана оценка предпочтений» — с Историей она бессмысленна: показанное и так уходит из выдачи само). `favoriteLine(targetIdx)` принимает явный индекс; при указании курсор корректно сдвигается, если удалённая строка была ДО него.

## Фристайл-режим (`.freestyle-overlay`) — живая генерация, основы заложены, визуал ещё не финальный
Полноэкранный просмотр, кнопка «▶ фристайл» в `.main-topbar` (нужен только сервер живым — `disabled={demo}`, НЕ зависит от того, генерировал ли что-то редактор). Owner прямо сказал: оформление продумаем позже, здесь только каркас.
- **НЕ проигрывает уже сгенерированную редакторскую выдачу.** Первая версия слайсила editor-mode `lines` по `fsGroupStart` — владелец поправил: каждая строфа должна генерироваться ЖИВО, отдельным вызовом `/api/generate`, прямо во фристайле. `fsGenerateOne()` — отдельная от редакторского `generate()` функция, всегда просит ровно `rhyme.length` строк (или 1 строку без схемы) — **ползунок «Строфы» из сайдбара сюда не относится вообще**, фристайл игнорирует `effectiveShortlist`.
- **Упреждающая подгрузка скрывает гэп генерации** (прямая просьба владельца: «надо учитывать гэп временной генерации при указе времени переключения»). Пока показана строфа N, `fsNextRef` уже держит промис на строфу N+1 (`fsStartPrefetch()`, вызывается явно сразу после каждого `setFsStanza`). `fsAdvance()` берёт готовый промис — если он уже разрешился, переключение мгновенное; если генерация не успела (медленные настройки/большая своя схема), просто ждёт её — `fsLoading` в этот момент показывает «генерируется…», а не зависает молча.
  - **Не реактивный `useEffect`.** Первая версия слушала `[freestyle, fsStanza]` разом — это стреляло генерацией ДВАЖДЫ на каждый переход (сработка на смену `freestyle`, отдельная сработка на смену `fsStanza`) плюс сам явный вызов = 3 живых запроса на один показ строфы, поймано по факту (6 запросов в сети на один вход во фристайл, ожидалось 2). Переделано на явные вызовы `fsStartPrefetch()` в трёх точках (`enterFreestyle`, `fsAdvance`, `fsRegenerateNow`) — по одному вызову на переход, без сюрпризов зависимостей.
  - **Побочно найден и исправлен реальный баг валидации.** `clean.knobs()` зажимал `shortlist` снизу к 5 — запрос ровно 4 строк (схема «абаб») тихо раздувался до 5. Нижняя граница снижена до 1 (влияет и на редакторский режим: 1 строфа × короткая своя схема тоже могла на это наткнуться).
- **Play (▶/❚❚)** — таймер САМОпланирующийся (`setTimeout`, не `setInterval`) — ждёт `fsSpeed` (1-15 сек), потом `fsAdvance()` (который сам дождётся генерации, если та не успела), потом планирует следующий тик — медленная генерация не может вызвать наложение тиков друг на друга.
- **Пауза без выхода — Space.** Показывает ВСЕ настройки: скорость/ширина строки (свои) + `renderSettings(true)` — тот же компонент, что в сайдбаре, компактнее (класс `.compact`). Поле темы + кнопка генерации свои — `fsRegenerateNow()` (НЕ `fsAdvance()`, специально: если владелец только что подвинул ползунок, `fsNextRef` мог начать готовиться ДО правки — переиспользовать его значило бы тихо проигнорировать правку; `fsRegenerateNow` всегда бьёт свежим запросом с текущими input/rhyme/knobs).
- **Ручной шаг — Enter**, **выход — Esc** (свой обработчик клавиш, редакторский явно отключается через `if (freestyle) return`, чтобы оба не реагировали на один Enter/Space разом).
- Проверено вживую полным циклом: вход без предварительной генерации в редакторе → ровно 4 строки для «абаб» (не 5) → play (автопрогон по таймеру, ровно 1 запрос/такт) → Space (пауза, настройки) → Enter (живая генерация новой строфы) → Esc (чистый выход) → редактор после выхода работает без ошибок.

## Индикатор фоновых процессов (topbar)
Маленькая точка справа от «принято: N» — цвет = худший статус среди пунктов `/api/status` (серый не начато → синий в процессе, пульсирует → жёлтый застопорилось → зелёный готово; красный ошибка, приоритет выше жёлтого/синего). Наведение раскрывает панель: для КАЖДОГО пункта всегда — прогресс-бар на всю ширину в цвете статуса + подпись мелким шрифтом (не только цвет — снятие показаний одним взглядом, без гадания). Список общий (`server.py: api_status()` возвращает массив) — новый фоновый процесс добавляется отдельной функцией в этот список, фронт (`App.jsx: StatusWidget`) не трогается.
- Единственный пункт сейчас — сборка `tools/build_nl_rhyme.py`: сравнивает `core/data/nl_rhyme.status.json` (сайдкар, скрипт пишет его хартбитом каждые ~30s, на старте, на каждом чекпоинте данных и при падении/завершении — Раунд 29; чекпоинты самого файла данных — по времени, раз в 5 мин, не «каждые 5000 строк») с живым `len(NL_STORE.state.fragments)` (НЕ `get_all_fragments()` — та пересобирает список из 274k+ словарей на каждый вызов; при опросе раз в 500мс это заметная лишняя работа, `len()` на существующем списке — нет). «Застопорилось» — не отдельное состояние скрипта, а суждение СЕРВЕРА: `state=running`, но `updated_at` старше 3 минут (комп заснул, процесс убит и т.п.) — проверено вживую (искусственно состарил timestamp, сервер корректно вернул `stalled`).
- Опрос раз в 500мс (было 20с) — по прямой просьбе владельца видеть прогресс в реальном времени.
- Если nakedlunch не установлен на машине — пункта нет вообще (не «серый», а отсутствует), там нечего собирать.
- **Автозапуск при добавлении источника.** `/api/nl/source/add` вызывает `_nl_rhyme_ensure_running()` — новые фрагменты начинают покрываться без похода в терминал. Двойная защита от дублирующего запуска: свой `Popen`-хендл (быстрая проверка) + чтение самого статус-файла на случай, если сборка уже идёт в ДРУГОМ процессе (ручной запуск владельцем, или предыдущий инстанс сервера) — без этого второй `ruaccent`-процесс мог бы гоняться за тем же файлом одновременно с первым.
- **Кнопка ручного запуска** («↻ прогнать ударения заново», рядом с «+ добавить файл» в секции nakedlunch-корпусов) — `POST /api/nl/rhyme/run` → `_nl_rhyme_ensure_running(full=True)`. **Всегда ПОЛНЫЙ пересчёт с нуля, не инкрементальный** (исправлено 2026-07-14 — владелец поймал, что кнопка технически «работала», но кэш и так был ~100% заполнен, поэтому инкрементальный прогон за секунды видел «всё уже есть» и завершался, реально ничего не пересчитав — выглядело как «не работает»). `tools/build_nl_rhyme.py --full` игнорирует существующий кэш (`existing={}`) и пересчитывает КАЖДЫЙ фрагмент заново — это то, что владелец явно просит нажатием ручной кнопки, в отличие от автозапуска при добавлении источника (`/api/nl/source/add`), который остаётся инкрементальным (там нужно быстро добрать только новое). Статус-сайдкар получил поле `mode` ("full"/"incremental"); топбар при `mode=="full"` добавляет «(полный пересчёт)» к лейблу — пометка остаётся видна и ПОСЛЕ завершения (до следующего запуска), так что видно, какой именно прогон только что состоялся, а не просто «готово». Проверено вживую реальным кликом в браузере: счётчик идёт от 0% (не сидит на 100% как раньше), лейбл с пометкой держится до конца и после.

## Работает (проверено на реальном пути)
Замкнутый цикл: **тема → выдача-последовательность → скан с клавиатуры → избранное в свою панель → сохранение**. Показанное автоматически уходит в Историю (обратимо) — см. «История и Избранное» ниже. Никакой алгоритмической коррекции выдачи на основе прошлых решений владельца (убрано 2026-07-14 — см. тот же раздел). Быстро на большом словаре.

- `core/`:
  - **Словарь: ~32k лемм** (18955 сущ. / 7144 прил. / 5889 глаг.) — открытый пул из самых употребимых русских слов (`core/data/lexicon.json`, wordfreq top-300k → zipf≥2.2 → pymorphy3 known-word фильтр → без имён/фамилий/топонимов). Плюс ~130 ручных «сид»-лемм с тематическими тегами для направленности.
  - **Согласование и ударение полностью запечены офлайн** в `core/data/forms.json` (lemma → грамматическая комбинация → (словоформа, индекс ударения)), собран `tools/build_forms.py` (pymorphy3 + ruaccent, один прогон ~6.5 мин на 257k форм). **Рантайм НЕ вызывает ни pymorphy3, ни ruaccent для генерации** — только dict-lookup. Подвижное ударение (холода́, звезда́, фонари́) верное по построению.
  - `generate.py` — слот-грамматика (6 шаблонов); тематический вес — **двухуровневая выборка** (60% из тематически-заякоренного тира, 40% из полного открытого пула), не аддитивный вес (аддитивный вес физически тонет в 19k-словном хвосте — было исправлено после регрессии).
  - `scan.py` — слоги, метр, рифмо-ключ.
  - `filters.py` — каскад: формальность → тавтология → банальность (wordfreq). Ранжирование — только внутренние свойства строки (метр для сгенерированных; тема-биас для nakedlunch — см. ниже), БЕЗ дистанции до истории владельца (λ убрана 2026-07-14). Сборка выдачи — жадная диверсификация (MMR): соседние строки не похожи. Исключает всё, что сейчас скрыто (`corpus.hidden_set()` — история + избранное). Кандидатские леммы берутся из `Word.lemma` (известны точно из генерации), эхо-возвращаются клиентом при добавлении в избранное — больше НЕ перепарсятся из текста (было узким местом и источником неточности на омографах).
    - **Отбор с рифмо-схемой — ранний выход, а не полный перебор (Раунд 56).** `_select_with_rhyme` искал максимум ранга обходом ВСЕХ кандидатов на каждой якорной позиции; на пуле в 40-60 тысяч (столько даёт слоговой резерв) и десятибуквенной оде это 688 секунд на одно звено. При выключенной связности ранг от позиции не зависит, поэтому обход идёт по предсортированному `(-ранг, номер)` и берёт ПЕРВОГО подходящего — тот же победитель, включая ничьи. Полный перебор сохранён там, где он обязателен: обход по рифмо-корзине (позиция-последователь) и включённая связность. Текст серии: **777 → 28 секунд**, одиночная строфа **1.9×**. Эквивалентность закреплена эталоном из 24 случаев (`tests/data/select_golden.json`) и сверкой на 1100 настоящих строках — 0 расхождений.
  - `corpus.py` — избранное (permanent) + история (reversible, см. ниже) + чёрный список; атомарная запись в `data/corpus.json`. Лемматизация текста кэширована по токену.
- `api/server.py` — Flask; при старте **прогревает** `forms.json` + частоты wordfreq (`generate.warm_caches()`, `filters.warm_caches()`, ~190мс), поэтому первый же запрос быстрый, а не только второй.
- `interface/` — React/Vite: слева скан-последовательность, справа панель избранного. Клавиши `↑↓/jk/A/G` (`R`/отклонить убрана).

## История и Избранное (заменили permanent seen-set + accept/reject + λ-предпочтения, 2026-07-14)
Владелец: «всё что отвечает за алгоритмическую оценку предпочтений пользователя и из этого коррекции выдачи текста — стоит убрать»; «показанные строчки перемещать в историю, можно вернуть, настроить срок хранения»; «минус — бессмысленна, убрать».
- **Избранное (`accepted` в `corpus.py`)** — permanent, единственный способ убрать: `POST /api/favorite/remove`. Кнопка «+» на строке (в редакторе И в Истории) вызывает `POST /api/favorite`. Никогда не влияет на ранжирование будущих строк (раньше — дистанция λ; убрано целиком).
- **История (`corpus.history`)** — КАЖДАЯ показанная строка (редактор — сразу после генерации; фристайл — только когда стенза реально ПОКАЗАНА, не когда просто прогружена в очередь наперёд, см. фристайл-раздел выше) автоматически исключается из будущих генераций до восстановления или истечения `retention_days` (пресеты как у nakedlunch: never/week/month/3m/6m/year, дефолт month; свой независимый стор). `corpus.hidden_set()` = активная (не истёкшая/не восстановленная) история ∪ избранное — это то, что реально фильтрует `filters.run()`.
  - Записи истории хранят `tags` (токены темы на момент показа) — для «восстановить по теме» (`POST /api/history/restore_theme`, честное пересечение целых токенов, без substring-шума).
  - UI: кнопка «история · N» в топбаре → модальная панель — поиск по тексту, восстановить по одной/по теме, очистить весь лог (избранное не трогает), выбор срока хранения. Лог НЕ пустеет по мере восстановления — уже вернувшиеся записи остаются видны с пометкой `expired`.

## Честно про качество
Словарь настоящий и большой; строки заметно богаче и разнообразнее прошлого раунда. Тематическая направленность работает (двухуровневая выборка), но за счёт объёма пула часть слов в строке — случайные редкие слова, семантически не связанные («каннские звёзды», «эндотелий и сон») — ожидаемое следствие «дешёвого генератора» без семантических слотов, отфильтровывается частично банальностью/метром, но не полностью. Компромисс осознанный: объём против безупречной связности.

## Ограничения (осознанные)
- Словарь = частотный срез + ручные теги на ~130 словах; не вся семантика на 32k слов размечена — тематическая связность работает через двухуровневую выборку, не через полную категоризацию.
- Пересборка словаря: `python tools/build_lexicon.py && python tools/build_forms.py` (~7 мин, нужен `pip install ruaccent`).
- Банальность пословная; фразовая (биграммы) — BACKLOG.
- **Масштаб пула nakedlunch (2026-08-01): 2 868 100 записей в `nl_rhyme.json` (946MB), ~40 книг залито в июне-июле.** Цена решения «всегда полная база» (Раунд 20) на этом масштабе: загрузка кэша ~9-11s и 5.5GB RSS при старте сервера; промах кэша строгой таблицы (`_score_strict_table` — любая НОВАЯ комбинация тема/банальность/no_mat за пределами 2 слотов) ~16s без темы / ~24-33s с темой или no_mat (после оптимизации Раунда 28; было 24-43s), всё плавает до ~2× под своп-давлением 16GB-машины. Даже при горячем кэше запрос копирует row-dict на ~каждый из ~1.9M активных фрагментов — секунды на запрос; бюджет p95≈1.2s недостижим без архитектурного решения (Фаза 1 PLAN.md, прогрев пулов). Подробности и отвергнутые альтернативы — DECISIONS.md Раунд 28.
- Схема рифмовки (абаб/абав/абба/абвб) реально влияет на выбор строк (`_select_with_rhyme`), применяется ПОСТРОФНО (блоками по len(scheme), не на весь shortlist разом). Рифма ищется по ВСЕМУ `scored`-списку (тысячи кандидатов), не по MMR-урезанному топ-300 — иначе поздние строфы не находили пару под уже занятое окончание. «Якорь» пары (первая строка группы) выбирается с проверкой, что для его рифмо-ключа ещё остался хотя бы один свободный партнёр (`key_count`) — без этого по score первой брались часто уникальные окончания без пары, и половина строф ломалась молча. Проверено: 10/10 строф абаб и абба совпадают по обеим группам на реальном прогоне. Стоимость (перемерено в Раунде 13 после смены формулы n — см. DECISIONS.md): на max ползунке «выдача» (200) с рифмой прогон ~350 мс (было ~3.3с на старой формуле n); `_select_with_rhyme` сам по себе — O(size × len(candidates)) — единственная стадия каскада, чья стоимость реально зависит от size², поэтому она первой чувствует любой рост n, и именно на ней сходятся оба находки Раунда 13: сузили n → эта стадия подешевела сильнее всех остальных вместе взятых.

- **Расстановка по позициям, а не подмес постфактум.** Раньше `nl_take` считался отдельно и вклеивался в готовую grammar-последовательность через страйд — это СДВИГАЛО все позиции и визуально ломало видимую схему рифмовки, даже когда сама grammar-последовательность была верной. Теперь при активной схеме `_nl_slot_plan(size, nl_quota)` резервирует конкретные позиции заранее, и `_select_with_rhyme` подбирает КАЖДУЮ позицию из объединённого пула (grammar+nl), требуя нужный тип слота — квота мягче, чем сама рифма (если для зарезервированного nl-слота нет валидного nl-кандидата, слот отдаётся grammar, а не наоборот).

Дискретные уровни, не непрерывная формула — якорная проверка «есть партнёр» в `_select_with_rhyme` бакетирует кандидатов по этому же префиксу для O(1) подсчёта; per-пара формула потребовала бы O(candidates²). Дефолт передвинут с 0.5 на 0.0 в `clean.py` и `App.jsx` — раз ручка ничего не делала с рождения, все существующие настройки де-факто откалиброваны под точное совпадение; дефолт 0.5 в момент оживления молча смягчил бы вывод у всех, кто слайдер не трогал. Вместе с глобальным дедупом extendo это выгрызало один и тот же фиксированный список (~2000-2400 шт.) до нуля при повторных генерациях с той же темой — измерено: -40 nl-выживших ЗА ПРОГОН, ровно на размер шорт-листа, 6 подряд вызовов = -240, дальше к нулю. Исправлено в `core/nlbridge.py: fragments_for_theme()` — паддинг теперь СЛУЧАЙНАЯ выборка из уже посчитанного `scored`-списка (не детерминированный префикс), бесплатно по стоимости (скан внутри `_get_non_used_for_bias` уже идёт по всему пулу независимо от `top_k`). Проверено: 10 одинаковых повторных вызовов после фикса — 400/400 nl-строк оказались РАЗНЫМИ, `nl_survived` держится на случайном уровне без деградации.
